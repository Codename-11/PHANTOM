# End-of-run synthesis card

After every terminal run, the **Synthesis tab** on the Runs page leads with a one-glance card answering the operator's first question: *"How did that go?"*

::: tip You can preview the card without running anything
Settings → Advanced → **Open wizard**, click through to Step 4. The wizard fetches the same synthesis renderer with stub data so you see the layout before your first real run completes.
:::

## What's on the card

**Header**

- **Posture donut** — 0–100 score with a strong / fair / weak rating chip. Color-coded: green = strong, amber = fair, red = weak.
- **Delta** — if the dashboard has a previous run to compare against, an up/down arrow shows the score delta vs. the prior run.
- **Outcome line** — one-line summary like `Completed · 5 ok · 1 blocked · posture 72/100 (fair)`.
- **Status pills** — run status, scope name, duration, policy mode (governed / operator-override).

**Three primary cards (grid)**

- **Objective** — your goal verbatim, plus a met / partial / unmet / unknown chip and the signal that drove the call ("Completed without failures." / "1 action blocked." / etc.).
- **Activity** — events, tool calls (succeeded / failed / blocked), artifacts, approval totals (granted / denied / allow-once / override / timeout).
- **Posture breakdown** — bars for coverage, risk, and hygiene components. Findings severity bar underneath when findings exist.

**Two follow-up cards**

- **Highlights** — 3–5 short lines (wins first, risks second, notes third). Each ≤ 110 characters.
- **Next steps** — clickable buttons routing to Rerun, Triage findings, Review approvals, Generate exec summary, or Edit scope. Empty state proposes "broaden scope or toolpacks."

## How posture is calculated

The score is a weighted average of three components, each 0–100:

- **Coverage (40%)** — successful tool calls ÷ attempted tool calls. A clean run with no failures lands at 100.
- **Risk (40%)** — `100 - (high+critical findings × 12) - (medium findings × 4) - (blocked actions × 4) - (failed actions × 6)`. Floor 0.
- **Hygiene (20%)** — base 50 + 30 if the replay says the run completed cleanly + 20 if artifacts were captured, − 20 if there were more than 3 errors.

Ratings: 75+ = strong, 50–74 = fair, < 50 = weak.

If a run has zero tool calls (pure-text answer, no actions), coverage defaults to 100 and the posture reflects mostly hygiene.

## Highlights — heuristic vs. LLM

By default, highlights and next steps are generated by deterministic heuristics in `server/runs/synthesis.js`. They're sound but generic: *"3 tool calls completed successfully", "1 action blocked by scope policy."*

You can flip a flag in **Settings → Advanced → LLM-generated synthesis highlights** to have the configured model rewrite highlights and next steps from the run's actual trace. The model gets a compact prompt (run summary + last 20 trace events) and returns JSON matching the same data shape. Output is enum-validated; anything malformed falls back silently to the heuristic.

Flag is **off by default** because:

- It costs a tokens-worth of provider quota per synthesis fetch.
- The heuristic is good enough for most runs.
- Default-off keeps first-time operators from being surprised by latency.

Try it on a run that's surprising or non-obvious — it's the difference between "1 action blocked" and "ffuf wordlist `/usr/share/wordlists/common.txt` got 403 on every path under `/admin/` — looks like the WAF is fingerprinting the User-Agent, try `httpx -title` for a cleaner probe."

See the [synthesis data shape reference](/reference/synthesis-shape) for the exact v1 schema.

## Why the same shape feeds three surfaces

The synthesis builder is intentionally **load-bearing across three callers**:

1. **Runs page Synthesis tab** — rendered via `window.SynthesisCard.render(host, synthesis)`.
2. **Onboarding wizard Step 4** — same renderer with a `preview: true` option that adds a "PREVIEW · sample data" banner.
3. **Dashboard posture trending** — recent-runs list uses `window.SynthesisCard.renderCompactRow(synthesis)` for each row.

That means there's one builder, one renderer, one data shape, and zero parallel derivation paths to drift. Adding a field on the card means adding it once, and three surfaces benefit immediately.

## API

| Endpoint | What it returns |
|---|---|
| `GET /api/runs/:id/synthesis` | The v1 synthesis for a real run. Heuristic by default; LLM-enriched if the flag is on. |
| `GET /api/runs/:id/synthesis?preview=stub` | A hand-tuned stub synthesis. Same shape; used by the onboarding wizard preview. |
| `GET /api/runs/:id/synthesis?enrich=1` | Ad-hoc LLM enrichment for one fetch without flipping the global flag. |
| `GET /api/runs/:id/synthesis?previousScore=N` | Synthesis with `posture.delta = score - N` filled in. |

## Caveats

- LLM enrichment is not cached — each `/api/runs/:id/synthesis` fetch with the flag on triggers a model call. A cache (keyed on `run.id + last trace seq`) is on the roadmap.
- The card assumes the run terminated. Running runs still render a card, but objective and outcome will say "unknown".
